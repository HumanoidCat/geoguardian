# Evidencia · H8.5 · Credenciales por variables de entorno, fuera del repositorio

**Fecha.** 2026-08-11
**Responsable.** Alejandro Josue Rodriguez Zamora
**Materia y criterio de rubrica.** Sistemas Operativos · SO-1

## Que se hizo

Ninguna credencial vive en el repositorio. El esquema es:

1. `.env.example` esta versionado y lista **los nombres** de todas las variables
   con el valor vacio. Sirve de plantilla y de documentacion.
2. `.env` contiene los valores reales, existe solo en la maquina de cada
   persona, y esta ignorado en `.gitignore`.
3. `docker-compose.yml` consume las variables con la sintaxis
   `${VARIABLE:?mensaje}` para lo que es secreto, de modo que el contenedor
   **falla al arrancar con un mensaje claro** si la variable no esta definida,
   en lugar de levantar con un valor por defecto inseguro.
4. Los valores no secretos usan `${VARIABLE:-valor}`, con un valor por defecto
   razonable.

Variables cubiertas: `POSTGRES_USER`, `POSTGRES_PASSWORD`, los roles de minimo
privilegio `DB_USER_ETL` / `DB_PASS_ETL` / `DB_USER_API` / `DB_PASS_API`, y las
claves de las fuentes externas `FIRMS_MAP_KEY`, `COPERNICUS_USER` y
`COPERNICUS_PASSWORD`.

## Como se verifico

No basta con que `.env` este ignorado hoy: hay que comprobar que **nunca** entro
al historial, porque un secreto commiteado sigue siendo recuperable aunque se
borre despues.

    cd geoguardian

    # 1. .env en todo el historial, en cualquier rama
    git log --all --pretty=format:'%h %s' -- .env

    # 2. archivos rastreados cuyo nombre contenga "env"
    git ls-files | grep -i env

    # 3. confirmar que .env esta ignorado y por que regla
    git check-ignore -v .env

    # 4. buscar valores de contrasena no vacios en todo el historial
    git grep -n -E "(PASSWORD|PASS_[A-Z]+|MAP_KEY)=.+" $(git rev-list --all) \
        -- .env.example docker-compose.yml | grep -v ':?' | grep -v ':-'

## Observaciones

**Un falso positivo que conviene dejar anotado.** La busqueda de la cadena
`POSTGRES_PASSWORD=` en el historial devuelve dos commits, `1fd614b` y
`048266d`. Al revisar que archivo cambio cada uno resulta que el primero
introdujo `.env.example` y el segundo modifico `docker-compose.yml`: en ambos
casos la cadena aparece sin valor a la derecha. Por eso el chequeo 4 filtra las
lineas con `:?` y `:-` y busca solo valores no vacios. Un chequeo que devuelve
resultados no siempre es un hallazgo, y valia la pena comprobarlo en vez de
suponerlo.

**Lo que este esquema no cubre.** Las credenciales viven en texto plano en el
`.env` de cada maquina. No hay gestor de secretos, ni rotacion, ni cifrado en
reposo. Para el alcance del proyecto es suficiente, pero el manual de operacion
(H13.2) tiene que decirlo explicitamente en vez de dar a entender que el manejo
de secretos es de nivel productivo.

**Pendiente al llegar a Kubernetes.** H8.6 introduce manifiestos, y ahi las
credenciales pasan a objetos `Secret`. Un `Secret` de Kubernetes esta codificado
en base64, no cifrado: si el manifiesto se versiona con el valor adentro, el
secreto queda en el repositorio igual que si estuviera en texto plano. Los
manifiestos tienen que referenciar el `Secret` por nombre y crearlo aparte.
