## Que hace esta historia, y por que ahora

D-05 fue precisada el 2026-08-20 y dejo escrito, con todas las letras, que
«produccion» significaba un espacio de nombres en una laptop, que eso contradice
el proposito del producto, y cual es el trabajo pendiente **y en que orden**:

> Publicar la API y la base; automatizar la ingesta diaria para que el dato se
> actualice sin intervencion; y recien entonces retirar el aviso de datos
> simulados. Los tres pasos dependen de que exista un modelo entrenado:
> publicar antes seria publicar un mapa que no estima nada.

**La precondicion se cumple desde el 2026-09-03.** H3.6 cerro con la tuberia
escribiendo en `analitico.riesgo` y H3.8 la dejo afinada. Esta historia hace el
**paso 1**, y el retiro del aviso queda condicionado a que la API lo permita, no
a que alguien decida que ya se ve mejor.

Esto no es alcance nuevo: es trabajo que D-05 declaro pendiente hace quince
dias. Lo unico que cambia es que ahora hay con que.

## Lo que ya esta decidido y NO se decide aca

| Decision | Donde |
|---|---|
| El visor y la API van **detras del mismo origen**; el visor llama a `/api` por ruta relativa y **no hace falta CORS** | **D-23**, punto 4 |
| `modo` y `origen` son campos distintos: que son los datos, y por donde llegaron | **D-23**, punto 3 |
| Si la API no responde, el visor lee el respaldo estatico **y lo declara en pantalla** | **D-23**, punto 2 |
| `DESTINO_API` es variable de entorno para apuntar el visor sin reconstruir la imagen | **SC-07**, y es lo que usa `visor-deployment.yaml` |
| La API elige repositorio por `GEOGUARDIAN_REPOSITORIO=postgres`, y `/salud` deduce el modo de **que implementacion respondio**, no de la variable | H6.2, `dependencias.py` |
| El ETL escribe con su propio rol de minimo privilegio, no por HTTP | H1.8, D-05 |
| Los manifiestos de Kubernetes siguen siendo el despliegue declarado del curso | **D-05** |

**Esta historia no reemplaza a k3d.** Los manifiestos de H11.2 a H11.4 son lo que
la rubrica de Arquitectura evalua y siguen en pie. Railway es lo que hace que el
sistema sea consultable por quien no tiene el repositorio, que es lo que D-05
dijo que faltaba.

## Una decision nueva que esta historia toma, y necesita su ADR

**Railway construye las imagenes desde el repositorio, en vez de bajarlas de
ghcr.io.** H11.1 publica las dos imagenes y H11.2 las consume **por SHA exacto**,
que es lo correcto: se despliega el artefacto que el CI construyo y probo.
Railway construyendo por su cuenta rompe esa propiedad — construye otra vez, y
nadie garantiza que salga el mismo binario.

Se elige igual porque los paquetes de un repositorio privado obligan a lo otro:
abrirlos al publico, o guardar un token de lectura en Railway. Lo primero
publica el codigo construido; lo segundo agrega un credencial que hay que rotar.
Para un despliegue de demostracion de un trimestre, reconstruir es el costo mas
barato de los tres.

**Queda como ADR D-43**, con esa perdida escrita y no disimulada, y con la
condicion de que si esto pasara a ser un despliegue de verdad, se vuelve a
ghcr.io por SHA.

## Criterios

| # | Criterio | Como se comprueba |
|---|---|---|
| CA-1 | **Tres servicios y la API sin puerta a la calle.** Base, API y visor. Solo el visor tiene dominio publico; la API se alcanza unicamente por la red interna del proyecto | Se pide la URL de la API desde fuera y **no responde**; se pide `/api/salud` por el dominio del visor y si |
| CA-2 | **Un solo origen, como manda D-23.** El navegador nunca hace una peticion a otro dominio: el nginx del visor reenvia `/api` a `DESTINO_API`. **Y `DESTINO_API` va sin barra final** | Se mira la pestana de red del navegador: todas las peticiones al mismo origen. Se comprueba que no hay ninguna cabecera CORS porque no hace falta |
| CA-3 | **El esquema se aplica con `aplicar_migraciones.py`, no a mano.** Las trece migraciones, en orden, y `control.migracion` como testigo. PostGIS presente, con su version declarada | Se corre el guion contra la base de la nube y se lista `control.migracion`; se consulta `postgis_version()` |
| CA-4 | **El dato llega por un camino declarado y contado.** Se dice cual de los dos se uso -restaurar el respaldo de `basedatos/respaldos/`, o correr el ETL contra la nube- y se cuentan las filas de cada tabla **contra las de la base local** | `contar_ingesta.py` y `contar_riesgo.py` contra las dos bases, con las dos salidas en la evidencia |
| CA-5 | **`/salud` dice `real`, y lo dice porque respondio PostgreSQL.** No porque una variable lo afirme: `modo_de` pregunta por la implementacion | Se apaga la base y se comprueba que la API **no** sigue diciendo `real` |
| CA-6 | **La API en la nube usa el rol de solo lectura de H1.8**, y se prueba que **no puede escribir** | Con las credenciales de la API se intenta un `INSERT` en `analitico.riesgo` y tiene que ser rechazado. Un rol de lectura que nadie probo escribiendo no esta probado |
| CA-7 | **El aviso de datos simulados se retira solo si `/salud` responde `real`**, y vuelve solo si la API cae. La logica sigue siendo la de D-23: dos campos, no uno | Se apaga la API y se comprueba que el visor **declara** que esta leyendo el respaldo del 2026-08-16, en vez de quedarse en blanco o mentir |
| CA-8 | **Ningun secreto entra al repositorio.** Las variables se documentan **por nombre** y los valores los pone Alejandro en Railway. `.env.example` se actualiza si hace falta un nombre nuevo | Se busca en el arbol cualquier cadena de conexion o contrasena antes de abrir el Pull Request |
| CA-9 | **El costo esta medido contra los 5 dolares**, no supuesto: consumo real despues de 48 h corriendo, y que pasa cuando se acaba | Captura del consumo en Railway, con la fecha, en la evidencia |
| CA-10 | **La documentacion permite repetirlo sin mi.** Que servicios, que variables, en que orden, y como se restaura si hay que empezar de cero | Alguien mas del equipo lo sigue y llega al mismo sitio, o queda anotado que no se probo |

**El control se prueba rompiendolo**, al menos de tres formas:

  1. `DESTINO_API` **con** barra final: el nginx concatena y produce `//distritos`.
     Tiene que fallar de manera visible, no en silencio -es el defecto que el
     comentario de `visor-deployment.yaml` documenta y que nunca se provoco de
     verdad-.
  2. La API apagada: el visor cae al respaldo **y lo declara**.
  3. La base apagada con la API arriba: `/salud` deja de decir `real`.

## Lo que NO cierra esta historia

- **La ingesta automatica.** Es el paso 3 de D-05 y va como historia aparte: un
  cron que corre solo es superficie que puede fallar sola, y merece sus propios
  criterios y su propia alerta.
- **`base_datos_conectada`.** Hoy `rutas.py` lo devuelve `False` cableado -con el
  comentario de H6.1 explicando que abrir la conexion era H6.2- y
  `verificar_h61.py` **exige** que sea `False`. Con la base publicada, la API
  diria `modo: real` y `base_datos_conectada: false` a la vez. El aviso del visor
  lo decide `modo`, asi que nada se rompe, pero **la API estaria mintiendo sobre
  su propio estado**. Son dos archivos de Cesar y esta historia no los toca: va
  como aviso, con esta nota como respaldo.
- **Retirar los archivos de `frontend/public/simulados/`.** Siguen siendo la
  degradacion que exige la Definition of Done de H6.6.
- **Los manifiestos de Kubernetes.** No se tocan. Ver arriba.
- **Un dominio propio.** El subdominio que da Railway alcanza para lo que D-05
  pedia: que se pueda consultar sin tener el repositorio.
