## Lo primero, porque cambia como se lee todo lo demas

**El flujo de despliegue NO despliega al cluster k3d del equipo.**

No puede: GitHub Actions corre en la nube y ese cluster vive en una maquina
detras de un router domestico, sin direccion publica. Lo que hace es **crear su
propio cluster k3d dentro del runner**, aplicar los mismos manifiestos,
comprobar que converjan, y destruirlo.

Esto no se descubrio al implementar: se decidio antes, con las alternativas
medidas, en **D-36**. Y lo que se pierde queda declarado alli y aca: **al
terminar no queda nada corriendo.**

El cluster persistente se actualiza cuando una persona corre
`infra/k8s/desplegar.sh`, que aplica **exactamente los mismos manifiestos**.

### Se comprobo que el control DISTINGUE

Un control que no puede fallar no se distingue de uno que no comprueba nada. Es
la mitad que falto en **I-20**, asi que se introdujeron cuatro defectos a
proposito:

| Defecto introducido | Resultado |
|---|---|

Los cuatro se revirtieron y el verificador volvio a 16 de 16.

## Las decisiones, y que descarta cada una

### El despliegue no construye las imagenes

Consume las que H11.1 publico, por SHA exacto. Reconstruirlas al desplegar
produciria un binario distinto del que se probo, y el despliegue dejaria de
decir algo sobre lo verificado.

Se bajan con `docker pull` y se importan al cluster con `k3d image import`, en
vez de dejar que Kubernetes las baje. Evita crear un `imagePullSecret` para un
registro privado, y hace que un fallo de red se vea como un fallo de descarga y
no como un pod en `ImagePullBackOff`, que se lee como un problema del
manifiesto.

### Ningun despliegue automatico queda en `latest`

La base declara `latest` para poder aplicarse a mano sin herramientas. El flujo
la reemplaza por el SHA del commit, y **el verificador comprueba que lo aplicado
no diga `latest`**.

Con `latest`, dos corridas del mismo manifiesto dan resultados distintos y nada
registra cual esta corriendo.

### La reversion de H11.4 se PROVOCA, no se declara

Es la parte que mas costaba hacer verificable.

Produccion despliega **dos veces a proposito**: primero `latest`, que establece
la revision 1, y despues el SHA del commit, que produce la revision 2. Sin el
primer paso no hay a que revertir, y `kubectl rollout undo` sobre una revision
unica **no hace nada mientras informa exito** — seria una reversion que no puede
fallar, o sea ninguna.

Y con el disparo manual `probar_reversion` se despliega una etiqueta que **no
existe**: el rollout no converge, la reversion entra, y se comprueba que el
sistema vuelve a la revision anterior. Es la unica manera de saber que el camino
de reversion funciona **antes** de necesitarlo.

Esto es una ventaja del cluster efimero que el persistente no tiene: provocar un
fallo para probar la reversion en un entorno real significa romper el entorno de
alguien.

### El resultado del trabajo sigue al despliegue, no a la reversion

Si el despliegue falla y la reversion funciona, el trabajo **sale en rojo igual**.

Sin ese paso, un despliegue roto saldria en verde por haberse revertido bien, y
nadie se enteraria de que produccion quedo en la version vieja. Una reversion
exitosa es una red que funciono, no un despliegue exitoso.

### La aprobacion se comprueba contra la API de GitHub

H11.3 y H11.4 piden aprobacion manual y explicita. Eso **no vive en este
repositorio**: son `environment:` con revisores, configurados en Settings.

Un flujo puede decir `environment: produccion` y salir verde aunque ese entorno
no exista o no tenga revisores, y entonces **la historia esta incumplida con el
CI en verde**. Es la forma de **I-25**.

`verificar_cd.py --comprobar-aprobacion` consulta la API y falla si el entorno
no tiene revisores. Es la unica manera de que una condicion que vive fuera del
repositorio quede vigilada por una maquina.

### La comprobacion estatica corre en el CI, no solo en el CD

`cd.yml` solo corre sobre `main`. Sin el modo `--manifiestos` en `ci.yml`, un
manifiesto roto se fusionaria a `dev`, de ahi a `main`, y recien alli se
descubriria — con el despliegue como primer aviso.

## Lo que falta para poder marcar las tres historias

**Ninguna de las tres se marca `[x]` con este PR**, y el motivo es el criterio
del propio proyecto: verificar ejecutando, no leyendo. El flujo todavia no
corrio.

| | Que falta | Quien |
|---|---|---|
| 1 | Agregar **Manifiestos de despliegue** a las verificaciones obligatorias de `dev` | PM, en Settings |
| 2 | Crear los entornos **pruebas** y **produccion** con revisores | PM, en Settings |
| 3 | Fusionar `dev` a `main`, que es lo que dispara el CD por primera vez | PM |
| 4 | Correr el flujo con **`probar_reversion`** y archivar la salida | PM |

Los tres primeros son configuracion, no codigo. El cuarto es la unica prueba que
cierra H11.4 de verdad.

**El paso 1 no es una formalidad.** Sin el, el trabajo nuevo corre, sale en rojo
si algo se rompe, y no impide fusionar. Es exactamente I-25, registrada hoy
mismo, y ya paso una vez esta semana con la observacion (c) del PR #229.

## Lo que esto NO demuestra

**Que quede algo corriendo.** El despliegue automatico demuestra que el
despliegue funciona; no deja un sistema en linea.

**Que el cluster persistente este al dia.** Se actualiza cuando una persona
corre el guion. No es entrega continua hasta el entorno persistente, y llamarlo
asi seria mentir en la memoria.

Las dos van a **limitaciones del documento IEEE**, no a una nota al pie.
