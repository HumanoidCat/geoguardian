## Dos cosas que no existian y sin las cuales nada de esto corre

Se encontraron **antes** de tocar Railway, leyendo el repositorio.

### 1. El arranque de la base solo existia dentro de docker-compose

Las cuatro extensiones y los cuatro esquemas los crea
`infra/docker/init-db/01-extensiones.sql`, que PostgreSQL ejecuta **solo cuando el
volumen esta vacio y solo desde docker-compose**. En cualquier base que no venga de
compose ese guion no existe, y la primera migracion cae:

```
Aplicando 001 001_control_migracion.sql ... FALLO
schema "control" does not exist
```

Comprobado el 2026-09-04 contra un PostgreSQL 16 recien creado, no supuesto.

`infra/preparar_base.py` aplica **ese mismo archivo leido del disco**, no una copia
de sus sentencias, y despues comprueba que las extensiones quedaron. El verificador
exige que sea asi: `ARRANQUE.read_text` tiene que estar en el codigo y no puede
haber ningun `CREATE` escrito dentro del guion.

### 2. La base tiene que llamarse `geoguardian`, y lo exige el DDL

Comprobado contra una base llamada `railway`:

```
Aplicando 003 003_seguridad_roles.sql ... FALLO
```

`basedatos/ddl/003_seguridad_roles.sql` nombra la base literalmente:

```sql
REVOKE ALL    ON DATABASE geoguardian FROM PUBLIC;
GRANT CONNECT ON DATABASE geoguardian TO geoguardian_etl, ...;
```

Es correcto -un `GRANT ON DATABASE` tiene que nombrarla- y **no se arregla
editando la migracion**: una migracion aplicada no se edita nunca, y el aplicador
compara su SHA-256 justamente para detectarlo.

`preparar_base.bases_que_exigen_las_migraciones()` **saca esa exigencia del DDL**,
no de una constante: recorre `basedatos/ddl/*.sql` buscando `ON DATABASE <nombre>`
y se planta citando el archivo y la linea. Si manana una migracion nombrara otra
base, el guion lo diria solo.

## CA-5 y CA-7 · Los dos apagones, medidos el 2026-09-14

Los dos exigen apagar un servicio de produccion -la base para CA-5, la API para
CA-7- y ver que el sistema **declare** lo que le pasa en vez de mentir. La logica
que prueban es la de D-23 y esta medida en local (H6.6). Lo que sigue es la
medicion en produccion, entre las 18:45 y las 18:53 UTC del 2026-09-14 (12:45 a
12:53 en Costa Rica), con los reinicios hechos desde Railway y el visor leido
desde un navegador en Costa Rica. Las horas son las del registro de cada
servicio y las del navegador (`new Date().toISOString()`), no las del reloj de
nadie.

### Antes de apagar nada: lo que dice el codigo

Regla del proyecto desde I-54: medir desde fuera dice que algo se ve raro, no por
que. Asi que primero se leyo el codigo, y de ahi salieron las dos predicciones
que la medicion despues confirmo:

- `frontend/src/datos/cliente.js`: `LIMITE_MS = 3000`. El visor pide `/api/salud`
  con `AbortSignal.timeout(3000)`; si la peticion se aborta **o responde no-ok**,
  cae al respaldo y declara el motivo. Son el mismo `catch` de `negociar()`: una
  API que no contesta y una API que contesta 500 llevan al mismo sitio.
- `backend/api/dependencias.py`: `modo_de()` devuelve `real` por el **tipo** del
  repositorio, no porque la base conteste. Y `_repositorio_postgres()` lleva
  `@lru_cache(maxsize=1)`: **una conexion para toda la vida del proceso**, abierta
  en `RepositorioPostgres.__init__` con `conectar(autocommit=True)`, sin
  reconexion. `esta_viva()` captura la excepcion y devuelve `False`; pero
  `ultima_ingesta()` la propaga a proposito (I-41), asi que con la base caida
  `/salud` responde **500**, no `modo: simulado`.

La consecuencia esperada, escrita antes de medir: al apagar la base, la API
responde 500 y el visor declara el respaldo; y cuando la base vuelva, **la API no
va a volver sola**, porque la conexion que guarda esta muerta y nadie la reabre.

### CA-7 · la API

**Restart** de `api` desde Railway (en sitio, sin reconstruir). Registro del
servicio:

```
18:46:00.445Z  INFO: Shutting down / Finished server process [1]
18:46:01.401Z  INFO: Application startup complete.
18:46:01.410Z  INFO: Uvicorn running on http://0.0.0.0:8000
```

**Un Restart deja el proceso apagado durante un segundo**, no veinte ni treinta.
La ventana de «20 a 30 segundos» que se anoto en el intento de la madrugada era
el tiempo que tarda el panel en reflejar el reinicio, no el apagon. Un segundo es
menos que los 3 s de `LIMITE_MS`, asi que **el visor no cae al respaldo, y no
debe hacerlo**: el navegador reintenta la conexion dentro del limite. Medido:
carga del visor a las 18:46:18Z, encabezado `Datos reales · API · contratos
1.4.0`; `/api/salud` en 200 en ocho lecturas seguidas (18:46:25Z a 18:46:46Z, 174
a 203 ms cada una).

Por eso el apagon largo de la API **no se puede provocar con Restart**, y en
Railway no hay forma de dejar un servicio apagado sin borrar su despliegue. Lo
que si se pudo medir en produccion es **el camino del respaldo con la API
respondiendo 500**, que en el codigo del visor es el mismo `catch` que la API
caida (ver arriba). Esa medicion es la de CA-5 y vale para los dos criterios; el
caso «la API no contesta en absoluto» sigue medido en local, en
`docs/evidencias/arquitectura-software/H6.6-aviso-de-origen/sin-api-respaldo.png`.

## Lo que esta historia encontro en otras piezas

### I-35 · `.gitignore` filtraba `.env` exacto

`.gitignore` tenia la linea `.env`, que ignora **un archivo con ese nombre exacto**.
Un `.env.railway` con contrasenas reales **no estaba ignorado**. Corregido a
`.env.*` con `!.env.example`, con el motivo escrito en el propio archivo.

El control del verificador tambien estaba mal: preguntaba `".env" in texto` y
**respondia que si mientras el hueco existia**. Ahora aplica los patrones a nombres
concretos e incluye el caso que tiene que quedar **fuera**.

### I-36 · Se purgo el volumen antes de desplegar la imagen nueva

Un directorio de datos inicializado por una imagen y servido por otra:
`collation version mismatch, 2.41 contra 2.31`. El orden correcto -imagen,
desplegar, **despues** purgar- quedo escrito en el runbook.

Y dentro de esa incidencia, otra: el intento de arreglarlo con
`REFRESH COLLATION VERSION` devolvio `invalid collation version change`, **y se
leyo como que el camino no servia**. Los registros de despliegue de Railway traen
la sentencia exacta: fallo en `template0`, que no se toca por diseno y no hacia
falta. `template1` **si** se habia refrescado en ese mismo intento.

### El reintento de conexion esperaba por errores permanentes

`basedatos.conexion.conectar()` reintentaba noventa segundos ante cualquier
`OperationalError`, incluida `database "geoguardian" does not exist` -que el
servidor ya habia contestado-, y despues mandaba a mirar `docker compose ps` con
la base en otro continente.

**Medido:** en un fallo de conexion psycopg no expone el `sqlstate` -ni
`error.sqlstate` ni `error.diag.sqlstate`-, asi que `except OperationalError` no
puede separar «el servidor no esta» de «el servidor contesto que no».

La correccion vive bajo una **excepcion de propiedad escrita antes de tocar el
archivo** (`docs/07-propiedad-archivos.md`), estrecha: solo `conectar()` y solo
`.env.example`. La solicitud completa, con la medicion, esta en
`gestion/solicitud-cesar-reintento-conexion-2026-09-05.md` y se le manda a Cesar
igual: lo que cambia es el orden, no que se le consulte.

`infra/probar_reintento_conexion.py` da **5 de 5** contra un PostgreSQL 16 real,
comprobando clase de excepcion, tiempo y mensaje en cada caso.

**Al probarlo aparecio un defecto de mi propia correccion**: dejaba salir el
`OperationalError` crudo, y los modulos que llaman a `conectar()` capturan
`ErrorConexion` y nada mas. Habria cambiado un mensaje limpio por un rastro de
pila. Se envuelve, y el sabotaje 4 lo comprueba.
