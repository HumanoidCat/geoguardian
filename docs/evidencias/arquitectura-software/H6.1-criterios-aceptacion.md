## El hallazgo que simplifica la historia

`contratos/simulados/datos.py` ya trae `RepositorioSimulado`, que **cumple el
protocolo `Repositorio` completo**. Está verificado en el CI: `contratos.verificar`
comprueba que lo cumple por estructura.

Eso significa que la API puede quedar funcionando de punta a punta hoy, sin base
de datos, sirviendo desde el simulado. El contrato ya previó esta situación: el
esquema `Salud` tiene un campo `modo` con valores `real` y `simulado`, y su
docstring dice que el frontend debe mostrar un aviso visible cuando sea simulado.

No es un atajo: es el diseño que los contratos anticiparon.

La decisión D-14 dejó al frontend consumiendo `frontend/public/simulados/*.json`
exportados a mano, y dice que *"cuando exista la API, el cambio es la URL del
`fetch`, en un solo módulo"*. Para que ese cambio sea de una línea, la API tiene
que devolver **la misma forma** que hoy tienen esos archivos, que es la del
contrato.

## Decisiones tomadas

### D1 · Los endpoints dependen del protocolo, no de una clase

**Decisión.** Cada endpoint recibe el repositorio por inyección de dependencias de
FastAPI, tipado como el `Repositorio` de `contratos/repositorio.py`. Una única
función decide qué implementación se entrega.

**Por qué.** Es el criterio de la rúbrica de arquitectura y no un adorno: cuando
H6.2 traiga el repositorio de PostgreSQL, **no se toca ni un endpoint**. Se cambia
la función que resuelve la dependencia. Si en cambio los endpoints importaran
`RepositorioSimulado` directamente, H6.2 obligaría a editar todos los archivos de
rutas, que es exactamente lo que el patrón existe para evitar.

También es lo que hace posible probar los endpoints sin base de datos, que es lo
que pide H6.2 en su enunciado.

### D2 · Ningún esquema se redefine

**Decisión.** Los modelos de respuesta son los de `contratos/esquemas.py`,
importados. La API no declara ni un `BaseModel` propio salvo para errores.

**Por qué.** El contrato dice de sí mismo que es *"el contrato mas importante del
proyecto: lo consume el frontend y define la forma de todo lo que cruza la
frontera del sistema"*. Una copia en la API sería una segunda definición que se
desincroniza en silencio: los contratos ya cambiaron dos veces en dos semanas, a
v1.2.0 por los códigos de distrito y a v1.3.0 por el SPI.

Si `contratos/` cambia, el CI rompe la API en el acto. Eso es deseable.

### D3 · La API declara que sirve datos simulados

**Decisión.** `/salud` devuelve `modo: "simulado"` mientras el repositorio sea el
simulado, y `base_datos_conectada: false`.

**Por qué.** Lo exige el docstring del contrato `Salud`, y es la regla de no
inventar datos aplicada a la frontera del sistema: quien consuma la API tiene que
poder distinguir una estimación real de un relleno. Avril ya tiene que mostrar ese
aviso, según la decisión D-14.

El valor no se escribe a mano: se deriva de qué implementación está activa. Un
literal `"simulado"` seguiría diciendo lo mismo el día que haya datos reales.

### D4 · Superficie de endpoints

**Decisión.** Solo lectura, y solo lo que el protocolo `Repositorio` ya expone:

| Método y ruta | Devuelve | Para quién |
|---|---|---|
| `GET /salud` | `Salud` | Frontend, al arrancar |
| `GET /distritos` | `list[Distrito]` | Visor, para dibujar el mapa |
| `GET /distritos/{codigo}` | `Distrito` o 404 | Detalle |
| `GET /distritos/{codigo}/mediciones` | `list[MedicionDiaria]` | Series por distrito |
| `GET /distritos/{codigo}/riesgo` | `Riesgo` | Tarjeta de riesgo |
| `GET /riesgos` | `list[Riesgo]` | Coropletas de una fecha |

**Por qué esta lista y no más.** Cubre lo que consumen las historias bloqueadas y
nada más. Los reportes de calidad y las métricas de modelos tienen endpoints
naturales, pero sus datos no existen todavía y agregarlos ahora sería publicar una
interfaz que devuelve listas vacías sin que nadie sepa si es un error.

**Sin endpoints de escritura.** La ingesta la hace el ETL conectándose a la base,
no por HTTP. Un endpoint de escritura sería una segunda puerta a los mismos datos,
con sus propios permisos que contradecirían los roles de H1.8.

**Una séptima ruta que no cuenta como endpoint.** `GET /` redirige a `/docs`,
porque al probar la API quedó claro que abrir la dirección a secas devolvía un 404
sin explicación. Va declarada con `include_in_schema=False`: es una comodidad, no
parte de la interfaz publicada. La superficie que OpenAPI describe sigue siendo la
de los seis endpoints acordados, y el criterio CA-4 lo comprueba.

### D5 · Un distrito que no existe es 404, no un error

**Decisión.** `GET /distritos/{codigo}` con un código inexistente devuelve 404 con
un cuerpo de error descrito en OpenAPI.

**Por qué.** El contrato es explícito: `obtener_distrito` devuelve `None` y su
docstring dice *"No lanza excepcion: la ausencia es un caso valido"*. Un 500 en ese
caso convertiría una consulta legítima en una falla del servidor.

## Criterios de aceptación

### Contrato e interfaz

**CA-1 · La API arranca y responde.**
*Verificación:* se levanta el servidor y `GET /salud` devuelve 200.

**CA-2 · Ningún esquema está redefinido en la API.**
Todos los modelos de respuesta provienen de `contratos.esquemas`.
*Verificación:* búsqueda en `backend/api/` de definiciones de `BaseModel`; solo
puede aparecer el modelo de error. Y comprobación de que cada respuesta declarada
es una clase importada del contrato.

**CA-3 · Los seis endpoints existen y responden la forma acordada.**
*Verificación:* se llama a los seis y cada respuesta se valida contra el esquema
del contrato construyendo el modelo Pydantic. Si la forma no coincide, falla.

### OpenAPI

**CA-4 · El documento OpenAPI se genera y describe todo.**
Cada endpoint aparece con su método, su ruta, sus parámetros y el esquema de su
respuesta. Ninguno queda sin descripción.
*Verificación:* se descarga `/openapi.json` y se comprueba que las seis rutas están
presentes, que cada una declara un `200` con esquema, y que los esquemas
referenciados existen en `components`.

**CA-5 · La documentación interactiva está disponible.**
*Verificación:* `GET /docs` devuelve 200.

### Arquitectura

**CA-6 · Los endpoints no conocen ninguna implementación concreta.**
*Verificación:* búsqueda en los módulos de rutas de `RepositorioSimulado` o de
cualquier import de `contratos.simulados`; el resultado debe ser cero. La
implementación se resuelve en un único lugar.

**CA-7 · Cambiar la implementación no toca ningún endpoint.**
*Verificación:* se sustituye la dependencia por un repositorio falso escrito para
la prueba, se llaman los endpoints y devuelven los datos de ese falso. Sin editar
ningún archivo de rutas.

Este criterio es el que demuestra el aporte a la rúbrica de arquitectura: no que
el patrón esté escrito, sino que **funciona**.

### Honestidad del dato

**CA-8 · La API declara que sirve datos simulados.**
*Verificación:* `/salud` devuelve `modo` igual a `simulado` y
`base_datos_conectada` en falso, y el valor se deriva de la implementación activa
y no de un literal.

**CA-9 · Los nulos del contrato viajan como nulos.**
Un distrito sin dato censal devuelve `poblacion: null`, no `0`. Un riesgo sin
modelo entrenado devuelve `nivel`, `probabilidad` y `explicacion` en null.
*Verificación:* se comprueba en la respuesta real de los endpoints.

**CA-10 · Un distrito inexistente devuelve 404.**
*Verificación:* `GET /distritos/00000` devuelve 404 y no 500, con cuerpo de error.

### Reproducibilidad

**CA-11 · Funciona en una máquina limpia.**
Desde el repositorio recién clonado y el entorno instalado, la API levanta y los
criterios anteriores pasan. Sin base de datos: esta historia no la necesita.
