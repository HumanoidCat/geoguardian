# Evidencia · H11.5 · El visor publicado como sitio estático

**Fecha.** 23 de agosto de 2026 · **Responsable.** Alejandro
**Rúbrica.** CICD · **Criterios.** `H11.5-criterios-aceptacion.md`
**Destino.** GitHub Pages, `https://humanoidcat.github.io/geoguardian/`

---

## Qué se hizo

El visor se construye y se publica desde un job del `ci.yml`, solo al empujar a
`main`. No se publica la API ni la base: eso sigue fuera de alcance por **D-05**.

Lo que hace publicable al visor es **D-23**, y fue un efecto secundario de H6.6
que nadie buscó: el visor negocia su origen una vez y, si la API no responde, lee
los JSON del respaldo y lo declara en pantalla. Un `npm run build` produce algo
que funciona solo.

---

## El defecto que esta historia existía para encontrar

**GitHub Pages sirve en un subdirectorio**, y ahí toda ruta absoluta de raíz se
rompe. Servido el `dist` desde `/geoguardian/`, antes de arreglar nada:

```
  /geoguardian/                     ->  200
  /simulados/salud.json             ->  404    <- lo que el bundle pedia
```

Y es peor de lo que parece: **en el sitio publicado el respaldo es el único
origen que existe**, porque no hay API a la que caer. El visor no habría mostrado
un error, habría mostrado nada.

### Por qué no bastaba con `base` en Vite

Son **dos problemas distintos**, y `base` resuelve solo uno.

| | Lo reescribe Vite | Se arregla con |
|---|---|---|
| `index.html`, `assets/` | Sí | `base: './'` |
| `RESPALDO` en `cliente.js` | **No** | `import.meta.env.BASE_URL` |

`RESPALDO` son cadenas que se arman en tiempo de ejecución. Vite no las ve. Lo
que esté escrito ahí es literalmente lo que pide el navegador, y con `base`
puesto y `RESPALDO` sin tocar el sitio habría cargado la interfaz **sin ningún
dato**.

Es la misma clase de defecto que I-08 y que el duplicado de H1.5: se ve bien
leyendo el código y solo aparece al ejecutarlo en las condiciones reales.

```bash
cd frontend && npm run build
mkdir -p /tmp/sitio/geoguardian && cp -r dist/* /tmp/sitio/geoguardian/
cd /tmp/sitio && python3 -m http.server 8099
```

```
=== referencias de index.html, pedidas de verdad:
  ./favicon.svg                      -> 200
  ./assets/index-CcXraiFs.js         -> 200
  ./assets/index-0wLPKUIR.css        -> 200

=== respaldo estatico:
  simulados/salud.json                     -> 200
  simulados/distritos.geojson              -> 200
  simulados/riesgos-sequia.json            -> 200
  simulados/riesgos-incendio.json          -> 200
  simulados/riesgos-lluvia_intensa.json    -> 200

=== /api/salud debe fallar, para que el visor caiga al respaldo:
  /api/salud                               -> 404
```

Ese último 404 es **el comportamiento correcto**: es lo que hace que
`negociar()` capture el error y lea el respaldo declarándolo, que es CA-3 de
H6.6 verificado ahora contra un origen real.

### El verificador, y la prueba de que sirve

`docs/herramientas/verificar_h115.py`, **20 comprobaciones**, sobre el `dist`
construido y no sobre el código fuente. Es deliberado: en `cliente.js` la ruta se
ve bien.

Un verificador que pasa no prueba nada si no se comprueba que **detecta el
defecto**. Se reintrodujeron los dos, uno por uno:

```
sin `${BASE}` en RESPALDO:
  FALLO  el bundle no pide /simulados/ con ruta absoluta de raiz
        encontrado: ['`/simulados/salud.json']. Tienen que colgar de
        import.meta.env.BASE_URL
  codigo de salida: 1

  FALLO  index.html no referencia nada con ruta absoluta de raiz
        absolutas encontradas: ['/favicon.svg', '/assets/index-CZCnbQaY.js',
        '/assets/index-0wLPKUIR.css']. Falta `base` en vite.config.js
```

## Las decisiones, y por qué

**GitHub Pages y no Vercel.** La rúbrica es CICD. Un despliegue configurado a
mano en un panel externo se evidencia con una captura; uno que vive en `ci.yml`
lo reproduce cualquiera que tenga el repositorio y pasa por la misma revisión que
el resto del código. Además no agrega una cuenta ni un proveedor.

**`base: './'` y no `'/geoguardian/'`.** Un valor fijo obligaría a Avril a entrar
a `localhost:5173/geoguardian/` para trabajar. Con `'./'` el servidor de
desarrollo sigue sirviendo en la raíz —Vite ignora el base relativo en
desarrollo— y el mismo `dist` funciona en cualquier subdirectorio, incluida la
raíz si algún día se publica en otro lado.

**Tampoco se lee de una variable de entorno.** `process` es `no-undef` en el
`eslint.config.js` de Avril, que aplica los globales del navegador a todos los
`.js`. Es el mismo tropiezo que ya documenta el comentario de `server.proxy`, de
H6.6.

**Solo desde `main`.** `dev` recibe trabajo a diario. Publicar desde ahí pondría
cualquier PR a medio revisar en la URL que se le pasó al Comité Municipal.

**El job espera a `frontend` y a `gestion`.** No se publica un visor cuyo linter
o cuyos verificadores de documentación estén en rojo.

## Excepción de propiedad

`frontend/` es de Avril. Esta historia toca **dos claves, no dos archivos**: la
`base` de `vite.config.js` y las rutas de `RESPALDO` en `cliente.js`. Declarada
en `docs/07-propiedad-archivos.md` con la misma forma que las de H1.6 y H6.6:
estrecha, por historia y escrita. **Avril revisa el Pull Request.**

## Lo que queda pendiente, y por qué la historia no se cierra todavía

**Falta habilitar Pages en la configuración del repositorio**, que es un ajuste
manual que no se puede hacer desde el código:

> Settings → Pages → Source: **GitHub Actions**

Hasta que eso esté y el job corra sobre `main`, **no hay URL viva**, y sin URL
viva no hay forma de verificar el criterio que de verdad importa: que un
participante del Comité pueda abrirlo desde su teléfono.

Marcar la historia ahora sería declarar cerrado algo que nadie ha visto
funcionando. Se cierra cuando la URL responda, con la captura correspondiente.
