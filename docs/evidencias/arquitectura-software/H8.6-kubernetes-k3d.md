# Evidencia · H8.6 · Manifiestos de Kubernetes corriendo en k3d local

**Fecha.** 2026-08-11
**Responsable.** Alejandro Josue Rodriguez Zamora
**Materia y criterio de rubrica.** Arquitectura de Software · Arq (orquestacion
de contenedores y entornos de despliegue)

## Que se hizo

Los **tres entornos** que exige la rubrica corriendo en un mismo clus­ter k3d
local, en espacios de nombres separados, definidos con kustomize.

    infra/k8s/
      base/                     comun a los tres entornos
        postgis-statefulset.yaml
        postgis-service.yaml
        postgis-configmap-init.yaml
        kustomization.yaml
      local/
        desarrollo/             namespace geoguardian-desarrollo, 1 Gi
        pruebas/                namespace geoguardian-pruebas,    3 Gi
        produccion/             namespace geoguardian-produccion, 5 Gi y 2 Gi de memoria
      README.md

Decisiones de diseno que no son cosmeticas:

- **StatefulSet y no Deployment**, porque la base tiene estado y necesita
  identidad estable y volumen propio.
- **Service headless** (`clusterIP: None`), para que el pod se resuelva por
  nombre en lugar de balancear entre replicas.
- **Las credenciales no estan en el repositorio.** El StatefulSet las lee por
  `secretKeyRef` de un Secret llamado `geoguardian-db` que se crea a mano en cada
  namespace. Un Secret de Kubernetes esta codificado en base64, no cifrado: si se
  versionara con el valor adentro, la credencial quedaria expuesta igual que en
  texto plano. Coherente con H8.5.
- **`PGDATA` en un subdirectorio** del volumen. Es el fallo mas comun al pasar de
  Compose a Kubernetes: el PVC llega con `lost+found` e `initdb` se niega a
  inicializar un directorio no vacio.
- **`/dev/shm` como `emptyDir` de 256 Mi**, equivalente al `shm_size` del
  `docker-compose.yml`. Sin eso PostgreSQL queda con 64 Mi y falla en consultas
  con ordenamientos grandes, que es justo lo que hara el ETL.
- **El arreglo de la incidencia I-02 viaja tambien aqui**:
  `--locale-provider=icu --icu-locale=es-CR` en `POSTGRES_INITDB_ARGS`.

## Como se verifico

    cd infra\k8s
    docker version
    k3d cluster create geoguardian --agents 1
    kubectl get nodes

    kubectl apply -f local\desarrollo\namespace.yaml
    kubectl apply -f local\pruebas\namespace.yaml
    kubectl apply -f local\produccion\namespace.yaml

    # Secret por namespace, fuera del repositorio
    kubectl create secret generic geoguardian-db --namespace <ns> ...

    kubectl kustomize local\desarrollo     # revisar antes de aplicar
    kubectl apply -k local\desarrollo
    kubectl apply -k local\pruebas
    kubectl apply -k local\produccion

    kubectl get pods --all-namespaces -l app.kubernetes.io/part-of=geoguardian
    kubectl get pvc --all-namespaces
    kubectl exec -n geoguardian-desarrollo postgis-0 -- psql -U geoguardian -d geoguardian -c "SELECT postgis_version();"
    kubectl exec -n geoguardian-desarrollo postgis-0 -- psql -U geoguardian -d geoguardian -c "\dn"
    kubectl exec -n geoguardian-produccion postgis-0 -- psql -U geoguardian -d geoguardian -c "SELECT current_database(), current_setting('TimeZone');"

## Observaciones

**Una incidencia real durante la verificacion, registrada como I-03.** El
clus­ter se creo correctamente pero `kubectl` no podia conectarse: k3d escribe
`host.docker.internal` como direccion del servidor de la API en el kubeconfig, y
en esta maquina eso resolvia a `192.168.40.27`, que no responde. Se estuvo a
punto de borrar y recrear un clus­ter que estaba sano. Se resolvio apuntando el
kubeconfig a `127.0.0.1`, y el README documenta crear el clus­ter con
`--api-port 127.0.0.1:6445` para que no vuelva a ocurrir.

**Hoy solo esta desplegada la base de datos.** La API y el visor entran cuando
existan sus Dockerfile e imagenes publicadas: historias H6.1, H5.1 y H11.1. No se
declara un Deployment de algo que todavia no se puede construir, igual que en
`docker-compose.yml`.

**Duplicacion conocida.** El SQL de extensiones y esquemas vive en
`infra/docker/init-db/01-extensiones.sql` y, copiado, en el ConfigMap. Si se
cambia uno hay que cambiar el otro. Esta anotado en la cabecera del ConfigMap. Si
se desincroniza una vez, se pasa a `configMapGenerator`.

**Lo que esta implementacion no demuestra.** Los tres entornos comparten un
clus­ter de un solo nodo trabajador en la maquina del Lead PM. No hay
balanceador real, ni almacenamiento de proveedor, ni alta disponibilidad, ni un
incidente de produccion que resolver. "Produccion" es el nombre de un namespace,
no un sistema en operacion. El manual de operacion (H13.2) tiene que decirlo asi,
sin adornarlo. Es la consecuencia que D-05 ya declaraba y que aqui queda
confirmada en la practica.

**Sin replicas ni respaldo automatico.** `replicas: 1` en los tres entornos: con
un solo nodo, mas replicas no darian disponibilidad real, solo consumirian
memoria. La estrategia de respaldo es la historia H1.10 y se prueba sobre
`docker compose`, no sobre el clus­ter.
