## Qué se hizo

El visor dejó de leer `frontend/public/simulados/*.json` y pasó a consultar la API
de H6.1. Los archivos no se borran: pasan a ser el respaldo cuando la API no
responde.

**Ningún componente cambió.** El diff no toca `frontend/src/componentes/`, ni
`interpolacion.js`, ni los estilos. Eso es la comprobación de que la costura que
Avril dejó puesta en D-14 estaba bien puesta, y es el resultado más importante de
esta historia.

---

## Lo que D-14 prometió y lo que resultó

> *"Cuando exista la API, el cambio es la URL del `fetch`, en un solo módulo."*

El módulo sí fue uno solo. La URL no: la API devuelve `list[Distrito]` y
`list[Riesgo]`, y el visor espera un `FeatureCollection` y un mapa indexado por
código. Hubo traducción de forma, y cupo entera en `cliente.js`.

| Qué | Estático | API | Quién traduce |
|---|---|---|---|
| Estado | objeto `Salud` | objeto `Salud` | nadie, coinciden |
| Distritos | `FeatureCollection` | `list[Distrito]` | `aColeccion()` |
| Riesgos | `{fecha, simulado, riesgos:{codigo:…}}` | `list[Riesgo]` | `aPaquete()` |

`simulado` pasó de leerse escrito dentro del archivo a **derivarse** de
`/salud.modo`. El `true` en duro del archivo estático seguiría diciendo `true` el
día que los datos fueran reales; `modo` no puede mentir, porque H6.1 lo deduce de
qué implementación respondió.

## Los dos hallazgos, que cambiaron el alcance

Al llamar dos veces al mismo endpoint para comparar con lo que espera el visor,
apareció esto:

    GET /riesgos?fecha=2026-08-16&tipo_evento=sequia

    intento 1   50801 bajo  0,46   50802 alto 0,53   50803 medio 0,79
    intento 2   50801 alto  0,70   50802 bajo 0,90   50803 alto  0,75
    intento 3   50801 medio 0,56   50802 alto 0,73   50803 bajo  0,64

**La misma consulta, tres respuestas.** El mapa habría repintado los ocho
distritos con colores distintos cada vez que el usuario cambiara de evento y
volviera, y habría parecido un defecto de las coropletas de Avril.

**Y el intento 2 tiene 50802 con nivel `bajo` y probabilidad `0,90`**, que desde
D-21 es imposible: `probabilidad` es P(nivel = alto). D-21 había quedado a medias
— definí el campo y no arreglé el único productor de ese campo que existe.

Los dos se corrigieron por la solicitud **SC-03**, contratos a **v1.3.1**, y
quedan registrados como incidencia **I-08**.

## Las cuatro decisiones de diseño, y por qué

### 1. El origen se negocia una sola vez

`App.jsx` pide la salud y los distritos a la vez con un `Promise.all`, y los
riesgos en otro efecto. Si cada llamada decidiera su origen por su cuenta, una
podría dar con la API arriba y la siguiente con la API caída.

Hoy eso sería **invisible**: los dos orígenes salen del mismo `RepositorioSimulado`
con la misma semilla. Cuando H6.2 traiga PostgreSQL dejarán de coincidir, y el
visor pintaría los riesgos de un mundo sobre los distritos de otro sin que nada
fallara.

La negociación es la propia consulta a `/salud`, memorizada como promesa
compartida: quien llegue primero la dispara y los demás esperan ese resultado. Una
sola petición, cero carreras.

### 2. `modo` y `origen` son campos distintos

`modo` dice **qué** son los datos. `origen` dice **por dónde** llegaron. El caso
que obliga a separarlos todavía no existe: el día que la API sirva dato real y se
caiga, el respaldo servirá dato simulado viejo. Con un solo campo, ese caso se
vería igual que el normal.

Y ya se observó una versión pequeña: con el respaldo sin regenerar, el visor
declaraba **contratos v1.3.0** mientras la API declaraba **v1.3.1**. Es
exactamente el riesgo que D-14 se había anotado a sí misma, y ahora es visible en
pantalla en lugar de estar solo escrito en un ADR.

### 3. Ruta relativa `/api`, con proxy de Vite

Un origen absoluto obligaría a habilitar CORS en `backend/api/aplicacion.py`, que
es archivo de César y que la excepción de propiedad de esta historia no autoriza.
Pero además, en el despliegue el visor y la API van detrás del mismo origen, así
que el permiso no haría falta y habría que quitarlo. La restricción de propiedad y
la buena arquitectura apuntaron al mismo lado.

### 4. Se consulta el día de hoy en hora local, y el vacío se muestra vacío

`toISOString()` devuelve UTC. Costa Rica es UTC-6: a partir de las 18:00 el visor
habría pedido el riesgo de mañana, **todas las noches**.

Si la API no tiene estimación para hoy, los ocho distritos quedan sin estimación y
así se dibujan. No se cae hacia atrás a una fecha anterior: mostrar la estimación
de ayer rotulada como la de hoy es un dato con forma válida y contenido falso, que
es como empezó I-04.

## Verificación ejecutada

Cargando el **`cliente.js` real**, no una copia, con `fetch` sustituido para
emular el proxy de Vite y la lectura de `public/`.

### Con la API arriba

    origen           : api
    modo             : simulado
    contratos        : 1.3.1
    motivo respaldo  : (ninguno)
    distritos        : FeatureCollection 8
    propiedades      : {"codigo":"50801","nombre":"Tilaran","area_km2":60,"poblacion":null}
    geometria        : Polygon
    riesgos sequia   : 2026-08-20 simulado=true 8 distritos
      50801          : nivel bajo, probabilidad 0.31
      50807          : nivel alto, probabilidad 0.79
    ir y volver a sequia da lo mismo: SI

La fecha consultada es la de hoy, no la fecha fija del exportador. Los niveles son
coherentes con las probabilidades.

### Con la API caída

    origen           : estatico
    motivo respaldo  : fetch failed
    distritos        : FeatureCollection 8
    riesgos sequia   : 2026-08-16 simulado=true 8 distritos

El visor sigue en pie y declara por qué. La fecha vuelve a ser la del exportador,
que es lo correcto: es el dato que hay.

### Con la API respondiendo 502

    origen=estatico  motivo=la API respondio 502

Un proxy sin destino detrás también degrada, y con el motivo distinto.

### Con la API arriba y sin estimación para hoy

    origen=api
      distritos en el paquete: 8
      sin estimacion         : 8
      con nivel              : 0

Ocho sin estimación, no una pantalla a medio cargar. Es el criterio CA-5, y lo
sostiene el completado de códigos que hace `aPaquete()`: la API solo manda los
distritos que tienen estimación, y un distrito ausente del mapa no lo contaría la
leyenda.

### Verificador automatizado

    python docs/herramientas/verificar_h66.py

    31 comprobaciones, todas en verde.

Comprueba CA-1 a CA-6, la idempotencia de I-08, la coherencia con D-21, y —lo que
más importa— que **cada campo que leen los componentes de Avril exista en lo que
produce el camino de la API**. Un campo perdido en la traducción no rompe nada:
deja un hueco en pantalla.

Entra al CI, junto con el `verificar_h61.py` de César, que estaba escrito desde el
19 de agosto y no lo corría nadie más que su autor a mano.
