## Que se hizo

`obtenerSalud()` empezo a devolver dos campos nuevos que ningun componente
pintaba: `origen` y `motivo_respaldo`. Se agregaron al aviso de la cabecera.

### Por que son dos ejes y no uno

- **`modo`** dice **que** son los datos: simulado o real. Lo decide la API segun
  que implementacion del repositorio respondio, asi que no puede mentir.
- **`origen`** dice **por donde** llegaron: la API, o los archivos estaticos que
  quedaron como respaldo.

Mezclarlos perderia el caso que importa: el dia que la API sirva dato real y se
caiga, el respaldo servira dato simulado viejo. Con un solo campo, eso se veria
igual que una tarde normal.

### Los cuatro casos

| modo | origen | Que se muestra |
|---|---|---|
| simulado | api | Banda de modo simulado |
| simulado | estatico | Banda de modo simulado + aviso de respaldo |
| real | api | Nada. Es el estado normal del sistema terminado |
| real | estatico | Solo el aviso de respaldo. Es el caso peligroso |

El texto del aviso cambia segun el caso. Con datos simulados dice que la API no
responde. Con datos declarados reales dice ademas que **pueden estar
desactualizados y no reflejan el estado actual del sistema**, porque ahi el
problema no es la falta de conexion sino que lo que se ve puede ser viejo.

`motivo_respaldo` trae el texto crudo del fallo y va en el atributo `title`: quien
diagnostica lo encuentra, quien no, no lo sufre.

### El color del aviso

Ambar, no rojo. El rojo esta reservado para riesgo alto: una banda roja aqui se
leeria como alerta climatica cuando lo que advierte es sobre la procedencia del
dato. Es el mismo criterio por el que la banda de modo simulado es azul pizarra.

## Como se verifico

Provocando los dos estados de verdad, no describiendolos.

**Con la API arriba:**

    uvicorn backend.api.aplicacion:app --port 8000
    npm run dev -- --port 5180

**Sin la API:**

    Stop-Process -Id (Get-NetTCPConnection -LocalPort 8000 -State Listen).OwningProcess -Force
    Test-NetConnection -ComputerName localhost -Port 8000 -InformationLevel Quiet   # False

Y recargando el visor en cada caso.

### El hallazgo que justifica la separacion de los dos campos

Al comparar las dos capturas, los conteos de la leyenda **no coinciden**:

| Origen | Alto | Medio | Bajo |
|---|---|---|---|
| API | 3 | 1 | 4 |
| Respaldo estatico | 3 | **4** | **1** |

Los archivos de respaldo devuelven riesgos distintos de los que sirve la API.
Estan desactualizados respecto de la fuente real.

**Sin el aviso, alguien habria mirado esa pantalla y creido que Cabeceras paso de
riesgo bajo a medio.** Lo que paso es que la API no respondio y el visor esta
mostrando datos viejos. No hay ningun error en pantalla: los ocho distritos se
pintan, la leyenda cuadra consigo misma, y todo se ve normal.

Es exactamente el escenario para el que se pidio separar `modo` de `origen`, y
aparecio solo al provocar el caso.

## Observaciones

**Un tropiezo del propio procedimiento de verificacion.** El primer intento dio
un falso negativo: el aviso no aparecia al "apagar" la API. La causa no era el
componente sino que `Ctrl+C` no habia matado el proceso de uvicorn, que seguia
escuchando en el 8000.

Se detecto porque `Invoke-WebRequest` sobre `localhost:8000/salud` pidio
confirmacion para analizar la pagina: eso solo ocurre cuando **hubo respuesta**.
Si la conexion hubiera fallado, habria dado error de inmediato.

Vale registrarlo: la verificacion se dio por fallida antes de comprobar que la
precondicion se cumplia. Comprobar el estado del proceso, y no confiar en que
`Ctrl+C` lo cerro, es parte del procedimiento.

**Caso todavia no observable.** La fila `real / estatico` de la tabla no se pudo
provocar: hoy los archivos de respaldo se generan del mismo simulado que sirve la
API, asi que su `modo` siempre es simulado. El camino esta implementado y el
texto diferenciado escrito, pero no verificado en pantalla. Se podra cuando la
API sirva datos reales desde PostgreSQL.
