## 2. Decisiones que no son obvias

### 2.1 Se instalan cinco paquetes y no los veinticinco

`requirements.txt` es compartido y trae las dependencias del proyecto entero:
pandas, geopandas, rasterio, scikit-learn, xgboost, shap, scipy. **La API no
importa ninguno.** Se rastreó la cadena de imports desde
`backend/api/aplicacion.py` y solo llega a `fastapi` y `pydantic`. Se suman
`uvicorn` para servir, y `psycopg` con `python-dotenv`, que entran al fusionarse
H6.2.

Instalar los veinticinco agregaría un par de gigas y varios minutos **a cada
construcción**, y H11.1 va a publicar esta imagen en `ghcr.io` en cada push. El
costo no lo paga esta historia: lo paga la cadena de despliegue.

No se parte `requirements.txt` en dos archivos porque es compartido y eso pediría
otra solicitud de cambio. Se filtra, así que **las versiones siguen viniendo de un
solo lugar** y no pueden desfasarse:

```dockerfile
RUN set -eux; \
    grep -E '^(fastapi|uvicorn|pydantic|psycopg|python-dotenv)' /tmp/requirements.txt > /tmp/api.txt; \
    test "$(wc -l < /tmp/api.txt)" -eq 5; \
    ...
```

El `test` de cinco líneas no es adorno. Si alguien renombra o quita uno de esos
paquetes del archivo compartido, **la construcción falla** en vez de instalar de
menos y dejar que la imagen reviente al arrancar. Hoy el filtro atrapa exactamente:

```
fastapi==0.115.6
uvicorn[standard]==0.34.0
pydantic==2.10.4
psycopg[binary]==3.2.3
python-dotenv==1.0.1
```

### 2.2 Por qué la API es multietapa

Lo pide el criterio CA-1. Y se sostiene sola: en la imagen final no queda `pip`,
ni su caché, ni `requirements.txt`, que es el archivo compartido con las
veinticinco dependencias del proyecto.

**Con honestidad sobre el tamaño:** los cinco paquetes traen rueda precompilada
—`psycopg[binary]` justamente por eso—, así que aquí no se compila nada y el
ahorro es modesto, del orden de decenas de megabytes. La separación vale por lo
que **no viaja**, no por un salto grande de peso. No se va a afirmar lo contrario
en la defensa.

### 2.3 El `.dockerignore` de la API tiene un nombre raro

Se llama `infra/docker/api.Dockerfile.dockerignore` y no `.dockerignore`.

El contexto de esa imagen es la **raíz** del repositorio, porque la API importa
`contratos/` y `basedatos/`. Docker buscaría entonces un `.dockerignore` en la
raíz — archivo nuevo de primer nivel, **fuera de la excepción concedida**.

BuildKit acepta un archivo por Dockerfile con el nombre
`<ruta-del-dockerfile>.dockerignore`, que tiene prioridad sobre el de la raíz. Así
el archivo vive dentro de `infra/docker/`, que es lo que se pidió. Requiere
BuildKit, que viene por omisión en Docker Desktop.

### 2.4 El visor no espera a que la API esté sana

```yaml
  visor:
    depends_on:
      - api        # sin condition: service_healthy
```

A propósito. El visor arranca igual y su cliente cae al respaldo estático
declarándolo, que es lo que pide el criterio CA-3 de H6.6. Obligarlo a esperar
haría que una API caída deje al visor sin levantar, que es peor.

La API sí espera a la base con `condition: service_healthy`, porque sin base no
tiene nada que responder.

### 2.5 `GEOGUARDIAN_REPOSITORIO` sigue en `simulado`

El repositorio contra PostgreSQL llega con H6.2 y todavía no tiene tabla para diez
de sus dieciséis métodos. Poner `postgres` por omisión rompería el visor de Avril.
Se deja como variable, así que se cambia sin reconstruir.

## 3. Dos defectos del verificador, encontrados al correrlo

**CA-3 falló dos veces seguidas, y las dos veces el defecto era del verificador y
no de las imágenes.** Se dejan escritos los dos, con su arreglo.

### 3.1 Primera corrida — falso positivo por `GPG_KEY`

```
CA-3 · Las imagenes no contienen credenciales ni el archivo .env ... NO CUMPLE
  FALLA: geoguardian-api tiene variables sensibles horneadas:
         ['GPG_KEY=A035C8C19219BA821ECEA86B64E628F8D684696D']
```

`GPG_KEY` la pone la imagen oficial `python:3.11-slim`. Es la huella pública de la
llave con la que Python verifica su propio tarball al construirse: es pública por
definición y nosotros no la pusimos. Mi comprobación buscaba la subcadena `KEY` en
el nombre de cada variable y no distinguía quién la había puesto.

**Cómo se arregló.** No con una lista de excepciones. El criterio pide que
*nosotros* no horneemos credenciales, así que ahora el verificador inspecciona
también la imagen base —leyendo el último `FROM` del propio Dockerfile, para que
cambiar la versión base no deje la comprobación mirando la imagen equivocada— y
solo escruta las variables que aparecen de más. Compara pares `nombre=valor`
completos, así que también atrapa una variable de la base cuyo valor reescribamos.

Una lista de excepciones habría tapado `GPG_KEY` por nombre y habría seguido ciega
a cualquier variable nueva de la imagen base.

### 3.2 Segunda corrida — la imagen base no estaba en el almacén local

El arreglo anterior descansaba en otra suposición, y también era falsa:

```
CA-3 · Las imagenes no contienen credenciales ni el archivo .env ... NO CUMPLE
  FALLA: no se pudo inspeccionar la imagen base `python:3.11-slim`, asi que no se puede
         distinguir lo que agregamos. Traela con `docker pull python:3.11-slim` y repeti.
  FALLA: no se pudo inspeccionar la imagen base `nginx:1.27-alpine`, asi que no se puede
         distinguir lo que agregamos. Traela con `docker pull nginx:1.27-alpine` y repeti.
```

Yo daba por hecho que construir una imagen deja su base en `docker images`. **No es
así:** con BuildKit las capas de la base pueden quedar solo en la caché de
construcción y no aparecer en el almacén de imágenes.

**Cómo se arregló.** El verificador hace `docker pull --quiet` de la base y
reintenta antes de dar el criterio por incumplido. Pedirle al que corre esto que
lo haga a mano era trasladarle un problema que el guion puede resolver solo. Si
aun tras traerla no se puede inspeccionar, **marca incumplido**: no da por bueno
un criterio que no pudo comprobar.

En la corrida final se ven las dos líneas `no estaba en el almacen local; se trae`
justo antes de las comparaciones, que es la prueba de que ese camino se ejecutó.

### 3.3 Por qué esto se deja escrito

Es el tipo de hallazgo que el verificador existe para producir. Si CA-3 se hubiera
dado por bueno leyendo el Dockerfile, nadie habría mirado la configuración real de
la imagen — y las dos veces el error estaba en el que miraba, no en lo mirado.

También es la razón de que el guion salga con código 2 cuando no hay Docker en vez
de saltarse las comprobaciones: **un verificador que pasa cuando no pudo verificar
nada es peor que no tenerlo.**

## 4. Un hallazgo que no arreglo aquí

**`base: './'` en `vite.config.js` y `try_files ... /index.html` en nginx no
conviven si el visor llega a tener enrutador.**

H11.5 puso `base: './'` para que el visor funcione bajo `/geoguardian/` en GitHub
Pages. Con eso, un `index.html` servido en `/a/b` buscaría sus assets en
`/a/assets/`, que no existe.

**Hoy no rompe nada:** `frontend/package.json` no trae `react-router` ni ningún
enrutador, así que no hay subrutas. El `try_files` queda como seguro para cuando
las haya, y el verificador lo reporta como aviso, no como criterio.

Para Alejandro y Avril: el día que entre un enrutador hay que decidir entre `base`
relativo y rutas absolutas. No se puede tener los dos. `vite.config.js` no es mío
más allá de la excepción de H6.6, así que lo reporto en vez de tocarlo.

## 5. Otra cosa que se declara

Dentro del contenedor la base se alcanza por el nombre del servicio, `db`. Pero
`basedatos/conexion.py` lee **solo** `POSTGRES_HOST_LOCAL`, nunca `POSTGRES_HOST`.
Ese nombre se eligió porque los guiones del ETL corren desde la máquina anfitriona;
aquí adentro queda engañoso —lo que se define es el nombre de un servicio, no algo
local— y aun así es la variable que hay que poner.

Renombrarla toca los guiones de H1.1 y H1.2, así que se deja y se documenta.
`POSTGRES_HOST` se define en el compose por coherencia con `.env`; hoy nadie la lee.

**El orden de la salida es la comprobación.** `db` aparece como `Healthy` **antes**
de que `api` diga `Started`: es el `depends_on: condition: service_healthy` de la
API funcionando. El visor arranca sin esperar a la API, que es lo decidido en la
sección 2.4.

### 8.4 Tamaño de las imágenes


**Los identificadores cruzan con los builds de 8.1 y 8.2.** El `ID` de la API,
`4ee0c15a7d3d`, es el prefijo del `manifest list sha256:4ee0c15a7d3d30ee...` que
imprimió su build; el del visor, `7b58d0acc2ba`, el de
`sha256:7b58d0acc2ba21f66a58...`. Las imágenes que están corriendo son las que se
acaban de construir, y no unas viejas con el mismo nombre.

`DISK USAGE` es lo que ocupan descomprimidas en el disco local; `CONTENT SIZE`, el
contenido que viajaría a un registro.

**Con honestidad sobre el multietapa.** La sección 2.2 ya lo dice y estas cifras no
lo contradicen ni lo lucen: el ahorro de peso es modesto, porque los cinco paquetes
traen rueda precompilada y no se compila nada. **El multietapa vale por lo que no
viaja** —`pip`, su caché y `requirements.txt`, ausente según 8.5—, no por los
megabytes. No se afirma otra cosa en la defensa.
