## 3 · La estrategia

### Que se respalda

La base `geoguardian` entera: los cuatro esquemas, sus datos, sus funciones, sus
disparadores y sus restricciones. **No** los roles; el porque esta en 3.3.

### Cada cuanto

**No hay una cadencia por reloj, y eso es deliberado.** No existe entorno alojado
-es D-05-, asi que no hay proceso que corra solo: la base solo existe cuando
alguien levanta `docker compose`. Una cadencia declarada contra una base que no
esta encendida seria un numero escrito al lado de nada, que es exactamente lo que
D-26 corrigio en H1.14.

La cadencia es **por evento**, y son tres:

| Cuando | Por que |
|---|---|
| **Antes de cada migracion que cambie el esquema** | Es el unico momento en que un error del propio equipo puede perder datos |
| **Antes de cada recarga masiva del ETL** | H1.1 tarda 870 s en reconstruirse; el respaldo tarda segundos |
| **Al cerrar cada sprint** | Deja un punto al que volver que corresponde a un estado declarado |

### Como se toma

    python -m basedatos.respaldar
    python -m basedatos.respaldar --etiqueta antes-de-h3.4

La etiqueta es opcional y sirve para reconocer despues **por que** se tomo ese
respaldo. El programa imprime el tamano y la suma SHA-256 del archivo, para poder
comprobar mas adelante que no se corrompio en el disco.

### Cuantos se guardan y donde

En `basedatos/respaldos/`, con el nombre `geoguardian-<marca-UTC>[-etiqueta].dump`.
Se conservan **los cinco mas recientes**; los anteriores se borran a mano. El
volcado completo pesa unos 3 MB, asi que cinco son 15 MB y no hay presion para
automatizar la rotacion.

## 4 · El procedimiento de restauracion, y son dos pasos

    1. Los roles tienen que existir en el cluster
    2. python -m basedatos.restaurar <archivo>

**Paso 1.** Si faltan `geoguardian_api` o `geoguardian_etl`, se crean aplicando
`003_seguridad_roles.sql`:

    python -m basedatos.aplicar_migraciones

`restaurar.py` lo comprueba y **se niega a seguir si faltan**, en vez de
restaurar a medias y devolver cero.

**Paso 2.** El archivo es uno de los que dejo `python -m basedatos.respaldar` en
`basedatos/respaldos/`. El programa recrea la base de destino vacia y deja que
`pg_restore` traiga todo lo demas. No hay que preparar nada mas, y eso esta medido: ver 3.1.

### 3.1 · El volcado se basta solo, y la primera version del programa suponia lo contrario

`restaurar.py` corria `01-extensiones.sql` antes de restaurar, por analogia con lo
que se descubrio en H1.15 -que **ninguna migracion numerada crea las extensiones
ni los cuatro esquemas**: los crea `init-db`, una sola vez, sobre un volumen
vacio-. `pg_restore` dijo que la analogia era falsa:

```
pg_restore: error: could not execute query: ERROR:  schema "analitico" already exists
Command was: CREATE SCHEMA analitico;
```

`pg_restore --list` sobre el volcado lo confirma:

```
  10; 2615 18053 SCHEMA - analitico geoguardian
  11; 2615 18054 SCHEMA - control geoguardian
  12; 2615 18052 SCHEMA - crudo geoguardian
   9; 2615 18051 SCHEMA - geo geoguardian
   4; 3079 18020 EXTENSION - pg_stat_statements
   2; 3079 16385 EXTENSION - postgis
   3; 3079 17463 EXTENSION - postgis_raster
```

**Las migraciones y un volcado son dos artefactos distintos con distinta
autosuficiencia.** Las migraciones asumen una base ya inicializada; el volcado se
describe entero a si mismo. Las dos afirmaciones son ciertas a la vez, y
confundirlas costo una corrida.

### 3.2 · pg_dump se invoca dentro del contenedor

    docker compose exec -T db pg_dump -Fc ...

**La razon es de version, no de comodidad.** `pg_dump` se niega a volcar un
servidor mas nuevo que el, y la version del cliente local depende de lo que cada
quien tenga instalado. Con el binario del propio contenedor, cliente y servidor
son la misma version por construccion, y la historia no agrega una dependencia a
la maquina de nadie.

`-T` desactiva la asignacion de terminal: sin eso, la salida binaria se corrompe.

### 3.3 · Los roles NO viajan, y es una decision de seguridad

`pg_dump` de una base no incluye los roles: son del cluster. El volcado trae las
entradas `ACL` -los GRANT de `003`- que los nombran, sin su definicion.

`pg_dumpall --roles-only` **si** los exportaria, **con sus contrasenas cifradas
dentro**. Eso convierte al respaldo en un secreto, y es el mismo criterio que
CA-3 de H6.0: un artefacto con credenciales no se versiona ni se comparte.

`003` ya esta en el repositorio y es reproducible. No se gana nada exportando
contrasenas para recuperar algo que se sabe regenerar, y se agrega un secreto que
hoy no existe. **CA-8 comprueba las dos mitades**: que el volcado no traiga
definiciones de rol, y que este documento diga como se recuperan.

## 5 · Como se demuestra que la restauracion es fiel, y sale de H1.7

`pg_restore` puede terminar en cero habiendo omitido objetos, asi que el codigo de
salida no demuestra nada. Lo que se compara es el **contenido**:

    1. manifiesto de `geoguardian`
    2. volcado
    3. restauracion en `geoguardian_restaurada`
    4. manifiesto de `geoguardian_restaurada`
    5. comparacion byte a byte

`generar_manifiesto.py` describe el contenido con sumas SHA-256 por tabla y **sin
marca de tiempo**, de modo que dos corridas sobre los mismos datos dan bytes
identicos. Esa propiedad se decidio en D-29 por otra razon -que dos personas
pudieran comparar sus datasets- y resulta ser justo lo que hace falta aca.

Los dos manifiestos se generan con la misma version y la misma fecha a proposito:
asi **cualquier diferencia viene del contenido y no de los argumentos**.

## 6 · Dos defectos propios, corregidos al correr

### 6.1 · El error culpaba a pg_dump cuando Docker no respondia

Con Docker Desktop cerrado, el programa decia «pg_dump fallo dentro del
contenedor». **`pg_dump` no habia llegado a ejecutarse.** Un error que nombra al
culpable equivocado manda a buscar donde no es.

Ahora comprueba que el demonio responda antes de volcar, y si no responde lo dice
con esas palabras.

### 6.2 · CA-4 reventaba en vez de fallar

La primera corrida completa termino con un traceback de Python en CA-4, y **se
comio el veredicto de CA-5 a CA-8**, que ya se podian evaluar.

Es el mismo defecto que reporte en `verificar_diagramas.py` el 2026-09-02, un dia
antes: un control que se cae se ve distinto de uno que falla, y quien lo mira no
sabe si el criterio no se cumple o si su maquina esta mal.

Cada criterio corre ahora aislado: si levanta una excepcion se registra NO CUMPLE
con el motivo, y los demas siguen.

## 7 · Un hallazgo del proyecto, no de esta historia

**El registro de migraciones es local a cada maquina, asi que una fusion puede
sustituir el archivo de una migracion ya aplicada sin que nadie la edite.**

Al correr `aplicar_migraciones` despues del `pull`:

```
ERROR: Hay migraciones ya aplicadas que no coinciden con el disco:
  006 006_analitico_riesgo.sql: el contenido cambio despues de aplicarse
Una migracion aplicada no se edita. Reverti el cambio y crea un archivo nuevo con el siguiente numero.
```

Nadie edito nada. H1.15 se hizo dos veces en paralelo, se fusiono la version del
PM (#211) y la mia quedo en un PR cerrado. Mi base tenia el esquema mio -con
`analitico.contribucion_riesgo`- y el repositorio traia el suyo.

**El control detecta la diferencia, que es lo correcto, pero no distingue
«alguien edito» de «gano otra rama», y el mensaje manda a revertir un cambio que
no existe.** Vale la pena que el aviso contemple el segundo caso.

Se realineo sin perder un dato: `analitico` estaba vacio -0 filas en las dos
tablas, comprobado antes de tocar nada-, asi que se borraron las dos tablas, se
borro la fila 006 del registro y se aplicaron 006, 007, 008 y 009. **`geo` y
`crudo` no se tocaron**, y en ninguna parte se uso `docker compose down -v`,
por I-05.

## 8 · Lo que esta entrega NO cubre, y se declara

- **No hay copia fuera de la maquina.** No existe entorno alojado (D-05) y copiar
  el volcado a otro lado exige un destino y una credencial que el proyecto no
  tiene. **Un respaldo que vive en el mismo disco que la base no protege del
  fallo que mas importa**, que es perder el disco. Queda declarado, no insinuado.
- **No es recuperacion a un punto en el tiempo.** PITR necesita archivado de WAL.
  Con un volcado logico se recupera al momento del volcado y nada mas.
- **La rotacion de los cinco se hace a mano.** Automatizarla exige un proceso que
  corra solo, que es lo mismo que falta para la cadencia por reloj.
- **No se probo en maquina limpia.** Todo esto corrio sobre un volumen ya
  inicializado. Es la misma casilla que quedo abierta en H6.0.

### 9.1 · Una observacion de esa corrida: la suma del volcado NO es estable

Tres corridas seguidas produjeron **el mismo tamano exacto -3 111 355 bytes- y
tres SHA-256 distintas**:

```
7a1367cd60134e85e7e274e0f811a18e8beae028e3983dc8be414ad862b07201
8af3d2dcbd01ede8860c2e6449f0eef3d384cda831e0b2cd57d069e1be1a64ba
29a4ec91cc9812eec180e0d678e886e97d0a92ce4cf2be3c0fe121e6e3007426
```

El formato `custom` de `pg_dump` lleva una marca de tiempo en su cabecera, asi
que **dos volcados del mismo contenido no son el mismo archivo**.

La consecuencia importa: **la suma del `.dump` sirve para detectar que el archivo
se corrompio en el disco, y NO sirve para comparar dos respaldos entre si.** Lo
que compara contenido es el manifiesto de H1.7, que si es estable porque D-29 le
quito la marca de tiempo a proposito. Por eso CA-2 se apoya en el manifiesto y no
en la suma del volcado.

## 10 · Como se reproduce

```
docker compose up -d db
python -m basedatos.verificar_h1_10
```

Necesita Docker y la base levantada, cargada con los datos de H1.1 y H1.2. Crea y
deja la base `geoguardian_restaurada`. Para borrarla:

```
docker compose exec -T db psql -U geoguardian -d postgres -c "DROP DATABASE geoguardian_restaurada WITH (FORCE)"
```

**En ninguna parte se usa `docker compose down -v`**, por I-05.
